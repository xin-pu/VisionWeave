### PL-2026-003 - Deferred Aries capabilities

- **Status:** Monitoring
- **Recorded on:** 2026-09-19
- **Scope:** First-release capability coverage against the Aries reference implementation.
- **Observation:** Aries offered batch image flow over `Mats`, automatic graph layout and edge routing, nested subgraph nodes, template matching, circle-grid calibration, OCR, and work-directory output export. The first release defers batch/collection flow (ADR-0003), automatic layout and subgraphs (ADR-0006), and the remaining node families (detailed design section 8).
- **Decision or next step:** Keep the deferrals as decisions rather than omissions, and re-evaluate after the first-release node catalog and the persistence path are working end to end.
- **Update (2026-09-19):** Both conditions of that trigger now hold — the first-release catalog runs end to end, and the persistence path saves and reopens it — so the re-evaluation has started, as the Aries single-image migration ([#44](https://github.com/xin-pu/VisionWeave/issues/44)). That is where the trade-off this entry wanted kept visible is made, against the 80 `BlockMat` classes the legacy solution holds: the common single-image operations come over, in batches ordered by whether a node can be tested without a curated sample image; the contour and batch families stay deferred because they need port values this build does not have (`Contours` per ADR-0003, and a collection of frames for the batch flow); and OCR, template matching, Hough, histogram, corner, and the Aries-private Effects blocks stay out until one of them is argued for on its own rather than carried across with the rest. The first batch — colour conversion, crop, median blur, and threshold — also records where this build deliberately departs from Aries: `CvtColor` accepts the conversions the definition declares instead of any `ColorConversionCodes` value, and drops the destination channel count because the frame's pixel format already states it; `Crop` takes four numbers rather than opening `Cv2.SelectROI`, because a parameter is document data and a run has to reproduce without a dialog; and the crop copies its rectangle instead of publishing `SubMat(rect)`, which is a view sharing the producer's buffer and therefore a second owner of memory the run believes it owns (ADR-0005).
- **Update (2026-09-19, second batch):** The smoothing and pyramid nodes followed as [#46](https://github.com/xin-pu/VisionWeave/issues/46): `Blur` and `Bilateral Filter` beside the two the first build shipped, `Adaptive Threshold` beside `Threshold`, and `Pyramid Down` and `Pyramid Up` in Transform, taking the catalog to thirteen types. The departures are the same kind as the first batch's. `Blur` declares one kernel size instead of Aries's `Size`, so all three smoothing nodes read the same parameter in the inspector. `Adaptive Threshold` narrows the rule to the two `adaptiveThreshold` implements, in the option vocabulary `Threshold` already declares, and refuses a colour frame with a diagnostic instead of letting OpenCV assert on it. `Pyramid Down` and `Pyramid Up` declare no parameters at all: Aries required a `Size`, so its pyramid could not produce the size the input implies, and the size the input implies is the one this build derives. Four nodes were deliberately left out and each says why in the issue — `Filter2D` needs a kernel representation the parameter kinds do not have, `Normalize` would have to answer what a mask means and which depth the result carries, the point scaling node has no consumer while the derivative batch plans to report the absolute gradient itself, and `Split` and `Merge` are multi-port nodes that need their own decision rather than arriving as a side effect of a migration.
- **Update (2026-09-19, third batch):** The derivative and edge nodes followed as [#48](https://github.com/xin-pu/VisionWeave/issues/48): `Sobel`, `Scharr`, and `Laplacian` in Filter, and `Canny` beside them, taking the catalog to seventeen types. The batch had been held back on the one question its nodes share, and it answers it as the second batch said it would: they report the absolute value of the signed derivative saturated into the eight bits of the layout they were given, because the preview refuses a `Gray16` or `Float32` frame and no node consumes one, so a frame that held the sign would be invisible to the user and unreadable to the next node. `Canny` reports the edges as a black and white map, in one channel whatever the input held, and refuses a low threshold that is not below the high one, since two thresholds without a weak range below the strong one compare like a single threshold. `Scharr` declares one axis rather than two orders, because OpenCV measures a Scharr gradient along exactly one axis at a time, and `Laplacian` defaults its aperture to one, the five point kernel, keeping the wider apertures for the Sobel-derived response that answers at a pixel's diagonals as well. `Sobel` offers the apertures one, three, five, and seven although the call accepts nine at this depth, so that every node taking an aperture takes it from one set. The point scaling node stays deferred for a changed reason: the derivative nodes now publish what it was meant to make visible, so it waits on a consumer of its own rather than on them.
- **Update (2026-09-19, fourth batch):** The morphology nodes followed as [#50](https://github.com/xin-pu/VisionWeave/issues/50): `Erode` and `Dilate`, and `Morphology Ex` beside them with its operation as an option, taking the catalog to twenty types and filling the Morphology category the design has carried since the first release. The kernel schema this entry has promised since the first batch is settled here, and settled the way batch two settled the blur kernel: the structuring element is stated as a shape — `rect`, `ellipse`, or `cross` — the side of a square, and a count of iterations, reusing the `kernelSize` parameter the smoothing and derivative nodes declare, because a parameter is document data and a kernel the user assembles is not a value this build can hold. The square is a declared narrowing of OpenCV's non-square `Size`: two size parameters would be a kernel whose shape and size disagree about what a kernel is. The frame question is answered the other way from the batch before this one: a structuring element reads the neighbours of a pixel and writes the type back, so these nodes accept every layout a frame can hold and report the one they were given, exactly as the two pyramid nodes do, and only the derivative batch narrows by depth, which it can because it changes the depth. Hit-miss morphology is not offered, because it needs a kernel of ones, zeros, and minus ones and a single-channel input, which is a different kernel from this one; and the anchor stays at the centre of the element, because a node that let it move would have to say which pixel of a kernel is its origin.
- **Update (2026-09-19, fifth batch):** The draw nodes followed as [#52](https://github.com/xin-pu/VisionWeave/issues/52): `Draw Rectangle`, `Draw Line`, and `Draw Circle`, taking the catalog to twenty-three types and filling the Draw category the design has listed since the first release. This is the batch where a node stops measuring and starts marking, and it exists for the one decision that difference brings: how a colour is a parameter. The inspector holds numbers and not colours, so a colour is three numbers named after the components a drawing call reads in order, `blue`, `green`, and `red`, each from zero to 255 and all three defaulting to white so that a mark on a mask needs nothing set. A frame of a single channel takes the first of them, which is what a scalar means to such an image and not a rule this layer invents; a node that mixed the three into a grey value would be performing an operation nobody asked for and calling it drawing. `filled` is its own switch rather than OpenCV's width of minus one, because a parameter whose value says another one does not apply is a parameter that hides a decision, and the line node declares no such switch at all, since a line has no inside. The frame question is answered as the morphology batch answered it and for the same reason: a drawing call reads pixels and writes the same type back, so every layout is accepted and the one it was given is reported, which is the opposite of the narrowing the derivative batch makes because that batch changes the depth. Each node copies the frame it was given and marks the copy, because a frame in this build has one owner and marking the frame it was given would change a value another node may still read; a shape that reaches past an edge is drawn up to it; and the line type stays OpenCV's default, because which pixels a slanted line touches is a rasterisation question and a node that offered every line type would be a node about rasterisation rather than about drawing a line. `Draw Contours`, the other node the design's Draw row names, stays out until the `Contours` value exists (ADR-0003).
- **Update (2026-09-20, sixth batch):** The contour pair followed as [#56](https://github.com/xin-pu/VisionWeave/issues/56): `Find Contours` in the new Contours category and `Draw Contours` in Draw, taking the catalog to twenty-five types. It is the first batch whose value is not a frame, and it exists for the decision that brings: what a contour set holds. It holds an ordered point sequence per shape, and nothing else — Aries published a `Mat` per contour beside a separate `Mat Hierarchy`, and this build publishes one immutable value instead, so no native buffer crosses a port and the nesting the hierarchy carried has nowhere to live. That absence is answered rather than hidden. The two retrieval modes OpenCV offers for expressing nesting are not declared, because with no field to report them they would return what `List` returns and call it something else; the default is `External` rather than the `List` Aries defaulted to, because "how many objects are in this mask, and where" is what the node is for and a hole is part of the shape that surrounds it; and a filled draw paints the inside of every contour it is given, because leaving a hole empty is a question about nesting that no node can ask. The other Aries parameters stay out for reasons of the same kind: the approximation mode is always the simple one, because both nodes of the pair read one value and a parameter that changes how many points describe a contour is a choice about representation, and the draw has no contour index, because an index into a list whose order the user cannot see from the document is not a choice, no offset, since a coordinate shift only means something beside the node that produced the crop it names, and no line type, as the fifth batch decided for the other three drawing nodes. `Find Contours` refuses a frame that is not a single channel of eight bits with a diagnostic naming the layout it needs, because a contour is found on the image a decision was expressed in, and it hands the call a copy of the frame rather than the frame itself, because the call rewrites the image it is given in some OpenCV builds; it creates no lease, since what it publishes owns no buffer. `Draw Contours` reads pixels and writes the same type back, so it accepts every layout, and a contour of fewer than three points has no inside to fill, so it is marked as the point it is — an ordinary answer from a mask that holds one pixel rather than a case that stops the run. The batch is also where an entry in this ledger turned out to be wrong: the migration was ordered by whether a node can be tested without a curated sample image, and this pair was expected to be the first that needs one. It does not, because a mask is a picture a test writes as easily as a step or a spike — a filled rectangle, and the same rectangle with a hole in it — and the boundary of a shape is decidable from the shape. The contour property nodes — `Bounding Rect`, area, moments — stay out, and now for a different reason: the value exists and the pair proves it, so what they wait on is a consumer of what they produce.
- **Evidence:** `docs/adr/0003-port-value-types.md`, `docs/adr/0006-editor-and-ui-commit-protocol.md`, `docs/design/visionweave-detailed-design.md`, `src/VisionWeave.OpenCv/Nodes/OpenCvNodeDefinitionProvider.cs`, `tests/VisionWeave.IntegrationTests/OpenCv/`, [#44](https://github.com/xin-pu/VisionWeave/issues/44), [#46](https://github.com/xin-pu/VisionWeave/issues/46), [#48](https://github.com/xin-pu/VisionWeave/issues/48), [#50](https://github.com/xin-pu/VisionWeave/issues/50), [#52](https://github.com/xin-pu/VisionWeave/issues/52), [#56](https://github.com/xin-pu/VisionWeave/issues/56).
- **Owner:** VisionWeave maintainers.
- **Review again:** Before the first-release node catalog is frozen.

### PL-2026-005 - File-backed input and output nodes

- **Status:** Implemented
- **Priority:** P1
- **Recorded on:** 2026-09-19
- **Scope:** The Input/Output node family of the first-release catalog: the image source and save-image nodes.
- **Observation:** The OpenCV layer now ships Gaussian blur and resize, so a native frame can be produced, transformed, previewed, and released by a real run, but the catalog has no node that reads or writes a file. The tests therefore supply frames through a test-only source definition, and no user workflow can start from a real image yet.
- **Decision or next step:** Add the file-backed source and save nodes together with the path-parameter kind and the work-directory rules the design defers, so that a saved workflow can be run end to end from the editor.
- **Update (2026-09-19):** The pair is delivered with the rules that make a path mean something, decided in ADR-0012. `ImageSourceExecutor` reads the file its required `path` parameter names as a color frame and publishes the read `Mat` as a lease it created and no longer owns; `SaveImageExecutor` is a sink that declares no output port, refuses a destination that already exists until the document's `overwrite` boolean is set, and writes through a temporary name in the destination folder so a failed or cancelled write never leaves a half-written image. A `Path` names a file relative to the folder that holds the document, the working directory travels with the run in `NodeExecutionEnvironment` rather than with the process, `WorkDirectoryPath.TryResolve` turns a declared path and that folder into an absolute path or a refusal without throwing, and a refused path fails the node that declared it with the diagnostic vocabulary the run already has. The shell runs such a document through `RunWorkflowCommand`, which refuses an unsaved document with `VW-FILE-004` because it has no folder to resolve against, refuses a document with validation errors, reports the outcome of a stopped run as an outcome rather than a fault, and draws the newest published image in the preview region through a frozen copy that outlives the frame. The composite — a real image read from the document's folder, resized, written beside it, previewed, and stopped while a node runs, with the lease ledger flat — is covered by the shell's own smoke test. An absolute path or a configured output directory stays deliberately out of scope per ADR-0012 decision 7 and is recorded as PL-2026-018.

### PL-2026-006 - Parameter values are not validated at the definition boundary

- **Status:** Implemented
- **Priority:** P1
- **Recorded on:** 2026-09-19
- **Scope:** Definition-boundary validation of node parameter values: kind, bounds, options, unknown names, and required values.
- **Observation:** The snapshot now merges each declared `ParameterDefinition.DefaultValue` under the values a document saved, so a node placed without an explicit value reaches the executor with its default. Nothing validates the saved values themselves: a text value where an integer is declared, a number outside `Minimum`/`Maximum`, an option outside `Options`, or a name the definition does not declare all travel through the snapshot unchanged, and an executor re-checks only the values it happens to read. A required parameter that also declares no default is absent from the snapshot, so `NodeParameterSet.GetInt32` throws `KeyNotFoundException` and the run reports it as `VW-EXEC-001` instead of refusing the document up front. `ParameterDefinition.IsRequired`, `Minimum`, `Maximum`, and `Options` are therefore schema data the editor can show but the build does not enforce.
- **Decision or next step:** Validate parameter values where the definition is resolved — in the snapshot factory or a dedicated validator — with diagnostics for a kind mismatch, an out-of-range value, an unknown parameter name, and a missing required value, so an unrunnable document is refused before a snapshot exists. Every OpenCV definition starts from a declared default today, which is why the shipped catalog runs as placed; keep it that way until this validation lands.
- **Update (2026-09-19):** `WorkflowValidator` now checks parameters where it already resolves a node's definition, so a document that reports any parameter diagnostic never becomes a snapshot and no unreadable value reaches an executor. `VW-PARAM-001` reports a value whose shape does not match the declared kind (including a fractional value for an integer parameter), `VW-PARAM-002` a numeric value outside `Minimum`/`Maximum`, `VW-PARAM-003` an option outside the declared set, `VW-PARAM-004` a name the definition does not declare, and `VW-PARAM-005` a required parameter with neither a saved value nor a declared default. A saved `null` counts as unset rather than a kind mismatch, and a disabled node is only shape-checked, because its required values never reach a run.
- **Evidence:** `src/VisionWeave.Application/Validation/WorkflowValidator.cs`, `src/VisionWeave.Contracts/Diagnostics/DiagnosticCodes.cs`, `src/VisionWeave.Application/Execution/WorkflowSnapshotFactory.cs`, `tests/VisionWeave.Application.Tests/Validation/WorkflowValidatorTests.cs`, `tests/VisionWeave.Application.Tests/Execution/WorkflowSnapshotFactoryTests.cs`, `docs/design/visionweave-detailed-design.md` (section 4.3).
- **Owner:** VisionWeave maintainers.
- **Review again:** When the editor writes parameter values into a document, or when a path parameter enters the catalog.

### PL-2026-007 - Deliver the persisted workflow vertical slice

### PL-2026-008 - Build the first Nodify editor vertical slice

- **Status:** Open
- **Priority:** P1
- **Recorded on:** 2026-09-19
- **Scope:** WPF UI bindings for document-backed nodes, ports, connections, selection, property editing, undo/redo, and run-state presentation.
- **Observation:** The foundation provides a WPF shell, the Domain document model, and editor commit rules, but it has not yet proven that Nodify interactions become reversible document commands without leaking UI objects into Domain or Application.
- **Decision or next step:** Implement one end-to-end canvas workflow: add nodes, connect compatible ports, edit a parameter, undo/redo each document change, and render validation/run diagnostics. Add a UI smoke test for this flow before expanding node families.
- **Update (2026-09-19):** The shell and semantic theme this slice builds on has landed, so the canvas has a placed and tested frame to fill: five named regions, a token dictionary that is the only file naming a colour, focus and contrast covered by tests, and a status area that already reports document state, the running operation, and the newest condition. The canvas region still presents a placeholder; putting the projection there is this entry's work.
- **Update (2026-09-19, canvas projection):** The projection is in the canvas region. `CanvasProjection` turns a committed document into node, port, and wire presentations and is rebuilt whole whenever the session reports a new document or projection; `CanvasViewModel` turns add, connect, disconnect, move, delete, undo, and redo into application commands and never edits the document itself. A refused gesture needs no rollback, because the projection it was drawn from is committed state that the refusal left untouched; delete is one command (`RemoveNodesCommand`) and therefore one undo unit, as ADR-0006 requires. An STA smoke test builds the real window over the application's resources and walks the flow — place from the catalogue, connect, select, delete, undo, redo, and the unchanged surface a refused connection leaves — and it is what caught a `StaticResource` declared after the template that reached for it, which failed while the shell drew its first node. What remains of this entry: property editing, run-state presentation, the minimap, copy and paste, automatic layout, and the diagnostics panel.
- **Update (2026-09-19, inspector and document commands):** Property editing and the diagnostics panel have landed, so the canvas is no longer the only editable surface. `ParameterEditorViewModel` presents one field per declared parameter kind and commits through `InspectorViewModel` into `SetNodeParameterCommand`, one parameter being one undo unit; a value the definition refuses is reported as a condition and changes nothing. The shell now has its document commands over the session (new, open, save, save-as, recovery, and the save/discard/cancel question they ask first), a read-only presentation for a document this build must not write back, and a searchable catalogue. Two defects were found by the acceptance flow rather than by a headless test: a redo of a coalesced parameter unit restored the value the unit's first edit set instead of the one the user settled on (`ICoalescingCommand.ContinueWith`), and an open adopted what it had read on a worker thread, where the window refuses the notification, so the surface kept the document it replaced and the selection of that document survived — `EditorSession.Read`/`Adopt` now separate the blocking read from the adoption, which runs on the thread the command started on. What remains of this entry: run-state presentation, per-node preview, the minimap, copy and paste, and automatic layout.
- **Update (2026-09-20, run-state presentation):** The canvas now says what a run did, so the last remainder of this entry that needed no new runtime contract is done ([#54](https://github.com/xin-pu/VisionWeave/issues/54)). `ShellStatus` keeps the newest `WorkflowRunSummary` beside the outcome it already derived from it, and `CanvasProjection` reads it as one mark per node: `Succeeded`, `Failed`, `Cancelled`, `Blocked`, or `Not run` in a word and in colour, with the time the runner measured for the nodes it measured one for (ADR-0013), and the run's own condition for that node in the tooltip. The decision the presentation rests on is that a mark belongs to a revision: a run describes one execution of one revision of one document and the summary carries both facts, so the marks are drawn only while the document on screen is the document that ran at the revision it ran at — the rule `ValidationProjection.Matches` already follows. An edit or another document clears them, a node move keeps them because a move moves no revision, and starting a run clears them until it reports. Nothing about a run enters `.vwflow`. A node that is still executing is deliberately left unmarked: `NodeRunState` is terminal-only and the runner has no progress seam, so a running mark would need an observer contract, a marshalling implementation, and an answer for a quarantined executor, which is a decision of its own. What remains of this entry: per-node preview, the minimap, copy and paste, and automatic layout.
- **Update (2026-09-20, node tags and the catalogue filter):** The catalogue has a second axis ([#55](https://github.com/xin-pu/VisionWeave/issues/55)). `NodeDefinition.Tags` carries the words a type is filtered by, and the OpenCV provider declares its twenty-three types out of one vocabulary, `OpenCvNodeTags`, rather than each definition writing a word of its own: the picker's row is built from the words the catalog actually holds, so one `filter` and one `filtering` would be two chips that each show half the answer. That vocabulary and those definitions are held together where each can see the other — the catalog's tests require every definition to carry a word out of the published set and every published word to be carried by some definition — so a chip cannot appear that nothing answers, and the shell's row is derived from the definitions rather than from the provider, which keeps the App layer free of a reference to it and lets a plugin's own words filter without the shell changing. Chips intersect rather than union, because each word a user adds asks for less: `mask` and `threshold` together offer the two thresholded nodes and not the six that carry either word. The row's first chip clears it, the chip in force is painted in the accent, and the summary and the notice name whichever filters are in force. The search box still matches only the name a user reads and the identifier a document stores; a search that answered with a word no entry showed would offer a type whose reason for matching the user cannot see. A definition's words are drawn beside the name it is chosen under, because a tag the user cannot see is a tag they cannot learn. Tags are catalog metadata and not document data, so no `.vwflow` field records them and a document written before this change loads identically, and they stay off the canvas, which already says what a type is and what the last run did to it. What remains of this entry: per-node preview, the minimap, copy and paste, and automatic layout.

### PL-2026-022 - Define one execution-duration ownership policy

- **Status:** Implemented
- **Priority:** P2
- **Recorded on:** 2026-09-19
- **Scope:** The relationship between executor-supplied `NodeExecutionResult.Duration`, the `WorkflowRunner` `TimeProvider`, and the duration exposed in node and run summaries.
- **Observation:** The runner now measures run and fallback node elapsed time using its injected `TimeProvider`, but it prefers a non-zero duration an executor returned. The built-in OpenCV executors measure their durations with `Stopwatch`, so one summary can combine a deterministic runner clock with real wall-clock executor durations. The behavior is safe, but it makes the meaning of a node duration ambiguous and prevents a fully deterministic duration assertion for built-in executors.
- **Decision or next step:** Choose and document one contract before duration-driven UX, telemetry, or policy is added: either executors own operation timing and the runner treats their duration as authoritative, or the runner owns all reported timing and executors stop measuring it. Preserve the ability to report a meaningful duration for executors that complete synchronously. If a clock reaches executors, introduce it through an execution-context contract owned by `Contracts`; do not couple OpenCV to Application or to a test-only clock. Add contract tests for zero, executor-reported, cancellation, and exception paths.
- **Update (2026-09-19):** The paths that hold under either contract are pinned now ([#39](https://github.com/xin-pu/VisionWeave/issues/39)): a node that never produced a result reports `TimeSpan.Zero`, whether it was cancelled or its executor threw, and `Run_reports_the_durations_the_clock_shows` already pins that a node reporting no duration of its own is measured by the run's clock, which is what keeps a meaningful duration for an executor that completes synchronously. The case that is left is the one this entry is about: `CompleteNodeAsync` prefers a non-zero `NodeExecutionResult.Duration` over the elapsed time the run measured for itself. That choice is not made here, because it decides what a summary means and the trigger that would force it has not arrived; what each side costs is recorded so the choice is cheap when it does. Run-owned timing makes every duration comparable, a plugin's included, and puts node durations under the injected `TimeProvider`, so a test can assert them exactly; it costs the four `Stopwatch` measurements in `VisionWeave.OpenCv` and any number an executor measured for work the run cannot see, and it needs a clock in the execution context only if a future capability has to measure that work itself. Executor-owned timing, which is what the code prefers today, keeps those measurements and needs no new contract; it leaves two meanings in one summary and keeps built-in executor durations out of reach of an exact assertion. The constraints this entry already states — one meaning per duration, and a deterministic assertion for built-in executors — point at run-owned timing, and the argument for the other side is a plugin measuring what the run cannot see, which stays speculative until a plugin contract exists.
- **Update (2026-09-19):** The maintainer chose run-owned timing on 2026-09-19, and it is implemented ([#42](https://github.com/xin-pu/VisionWeave/issues/42)) with the decision recorded as [ADR-0013](../adr/0013-execution-timing-ownership.md). `NodeExecutionResult` no longer carries a duration and `Success`, `Failure`, and `Cancelled` take none, so an executor cannot report a number the run did not observe; the four `Stopwatch` measurements in `VisionWeave.OpenCv` are deleted rather than kept as numbers nothing reads, which also leaves no clock for an executor to reach; and `CompleteNodeAsync` reports the elapsed time the run measured around the executor call, on the same clock the run measures itself on. The cancelled and exception paths keep reporting `TimeSpan.Zero`, the one part of the contract the ADR names as revisitable if telemetry ever asks for a partial measurement. Three tests pin the contract: `Run_reports_the_durations_the_clock_shows` (a node's report and the summary come from the injected clock), `A_node_that_answered_with_a_failure_is_measured_by_the_run` (a failure result is a completed execution, so it is measured too), and `Execution_contract_carries_no_timing_and_no_clock` in the architecture suite, which reads the public surface of `NodeExecutionRequest` and `NodeExecutionResult` so the timing slot cannot return one member at a time; the last one was confirmed to fail when a `TimeSpan Duration` property was added back and pass once it was removed.
- **Evidence:** `docs/adr/0013-execution-timing-ownership.md`, `src/VisionWeave.Application/Execution/WorkflowRunner.cs` (`RunNodeAsync`, `CompleteNodeAsync`), `tests/VisionWeave.Application.Tests/Execution/WorkflowRunnerClockTests.cs`, `tests/VisionWeave.Application.Tests/Execution/WorkflowRunnerCancellationTests.cs`, `tests/VisionWeave.Application.Tests/Execution/WorkflowRunnerResourceTests.cs`, `tests/VisionWeave.ArchitectureTests/Contracts/ExecutionTimingContractTests.cs`, `src/VisionWeave.Contracts/Execution/NodeExecutionResult.cs`, `src/VisionWeave.OpenCv/Execution/ImageSourceExecutor.cs`, `src/VisionWeave.OpenCv/Execution/ResizeExecutor.cs`, `src/VisionWeave.OpenCv/Execution/GaussianBlurExecutor.cs`, `src/VisionWeave.OpenCv/Execution/SaveImageExecutor.cs`, `docs/ledger/project-improvements.md` (PL-2026-010), [#39](https://github.com/xin-pu/VisionWeave/issues/39), [#42](https://github.com/xin-pu/VisionWeave/issues/42).
- **Owner:** VisionWeave maintainers.

### PL-2026-026 - Keep framework-templated controls out of the shell's data templates

- **Status:** Implemented
- **Priority:** P2
- **Recorded on:** 2026-09-20
- **Scope:** Which control styles the shell may use inside a `DataTemplate`, and what verifies that a binding the shell declares resolves.
- **Observation:** The shell reported `System.Windows.Data Error: 40 : BindingExpression path error: 'PressedForeground' property not found on 'object' ''ContentPresenter''` from its own inspector. `PressedForeground` is declared by `Wpf.Ui.Controls.Button` and bound by that control's own control template, in a `MultiTrigger` whose conditions are both `IsMouseOver` and `IsPressed`, setting `TextElement.Foreground` from `{Binding PressedForeground, RelativeSource=TemplatedParent}`. An element generated from a data template is templated by its item container, so every one of those template-parent bindings on the shell's one framework button drawn inside a data template — the inspector's browse action on a path parameter, whose item container is a `ContentPresenter` — resolves against that container instead of against the control: six properties the `ContentPresenter` does not declare, of which the report names one. Nothing fails and nothing blanks; the control silently loses its pressed and hovered look, and because the trigger needs both conditions the fault reports only while a user holds the button down, which is why pressing every button in the tree on a built window reproduced nothing.
- **Decision or next step:** The shell does not draw a framework-templated control inside a data template. `Shell.FieldIconButton` is based on the shell's own `Shell.ActionButton` (`TargetType="Button"`, a template the shell owns) rather than on `{x:Type ui:Button}`, and the inspector's browse action is a plain `Button` hosting a `ui:SymbolIcon`; `Shell.CommandButton` stays the framework button's style because the top bar draws it directly rather than from a template. The fault is caught rather than remembered: `MarkupBindingAudit` starts a listener on the binding trace source before the smoke test builds the window, and for each state the smoke flows reach it reports every trace message WPF raised and every control whose template is applied while its templated parent is that container and does not declare a property the template binds through it. That second check is the one that matters here, because it finds the fault on an idle window rather than waiting for a user to press the control. It lives in the smoke test because WPF allows one `Application` per process, so the smoke test is the only place a real window exists.
- **Update (2026-09-20):** Implemented on `feat/62-wpf-preview-processing` ([#62](https://github.com/xin-pu/VisionWeave/issues/62)). The audit replaced a diagnostic probe that reproduced the report by inspecting live elements: with the browse action still on the framework button's template the probe found the six unresolved template-parent bindings on exactly that control and none on the other sixty-five buttons of the tree, and with the shell's own template in place the audit reports nothing while the flows drive the window through a document, an inspection, and two runs. The audit also covers the tiles PL-2026-025 added, which are the newest markup drawn from a data template.
